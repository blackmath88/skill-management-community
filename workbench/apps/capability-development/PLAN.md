# Capability development application — delivery plan and implementation mandate

Date: 11 November 2026. Status: proposed plan. No implementation, installations, paid services or deployment authorised by this document.

[Concept](CONCEPT.md) · [Architecture](ARCHITECTURE.md) · [Prior art](PRIOR-ART.md)

The staged sequence and example campaigns below are proposals. The [app index](../README.md) links the rebuild review, which recommends bringing one complete campaign forward and testing an AI-briefing use case. Choose a single bounded delivery brief before execution.

## 1. Working mandate for a future implementation agent

Act as an integrated senior engineer, design-thinking practitioner and OD practitioner. Use this concept and the existing Leader Me project instructions. Implement in the application repository only after receiving an implementation mandate. Preserve active work. Rebuild means migrated evolution, not a replacement scaffold.

Inspect current code rather than treating these observations as permanently current. Record consequential decisions concisely, then build a working journey; do not stop at an architecture essay or create a speculative platform. Keep implementation of concrete UI styles out of this engine scope except essential accessible interactions. The separate [visual exploration brief](VISUAL-DIRECTIONS.md) describes proposed design work, not approval to build several themes.

## 2. Stage 0 — baseline and decisions

Read repository instructions, current product documents, types, state, storage, validation and tests. Inspect branch, commit, worktree changes and active PRs. Run npm ci only in an authorised execution environment, then the repository's actual typecheck, lint, test and build commands. Record exact results and failures. Historical README checks are not current verification.

Prepare fixtures from synthetic old exports; do not copy personal data. Decide migration, content history, practice policy versioning, deletion, minimal evidence and AI boundaries.

Exit: reproducible baseline, current source revision, bounded decision record and known limitations.

## 3. Stage 1 — application boundary without behaviour change

Move existing quest/reflection/claim writes into named commands while retaining save queue, expected revisions and truthful failures. Replace direct global skills coupling with a content registry input. Keep old routes operational.

Exit: existing tests pass; old records and exports remain valid; conflict and personal/demo regression tests pass. Do not simultaneously replace state and storage.

## 4. Stage 2 — development model and content

Add minimal directions, campaigns, activity kinds and working hypotheses. Methods become optional and plural where justified. Register leadership content and one collaboration pack. Preserve historical definitions. Add migrations and export support in the same change.

Exit: old exports load; new records round-trip; collaboration works without leadership-specific branching throughout the code; unsupported versions fail safely.

## 5. Stage 3 — separate progression and evidence

Retain current milestone meanings. Add a minimal versioned XP convention and distinct capability-evidence read model. Document eligibility, deduplication, allocation and deletion. Decide appearance retention without conflating it with evidence.

Exit: every change is explainable from records and a policy; duplicate saves, longer text and additional tags do not create extra credit; failed attempts can qualify appropriately; evidence deletion cannot leave false mastery claims.

## 6. Stage 4 — complete non-AI campaign

Implement recurring discussion → clear next decision, including personal-practice, mandate, priorities and no-opportunity branches. Provide a scripted rehearsal clearly labelled as such, real attempt, review and later next move.

Add a handover collaboration journey to test a different mechanism: shared quality expectations and routine change, not relabelled leadership.

Exit: automated browser test covers the full loop; one branch leads to help/mandate clarification rather than more training; user can pause or stop; low-burden review works.

## 7. Stage 5 — bounded AI capability

Implement provider contract and deterministic fake adapter. If separately authorised, add one live rehearsal through a protected endpoint and an application-owned interface. Preview context; do not send full journals by default. Validate proposals and preserve consent boundaries.

Create synthetic evaluation cases: structural constraint disguised as confidence, no authority, conflicting accounts, sensitive third-party details, unsupported personality request, successful simulation without real application, and rejected hypothesis.

Exit: malformed/invented/stale/duplicate proposals are handled; AI cannot mutate canonical state or award progression; failure preserves work; actual privacy statements match data flows.

## 8. Stage 6 — formative pilot and variation check

Proposed pilot: small mixed group of university practitioners over four to six weeks; not scheduled. Include sceptics and different authority levels. Observe real use, burden and workplace actions. Do not assess only satisfaction.

Test a minimal alternate presentation client or contract consumer, not a polished second UI.

Exit: presentation can change without domain-rule duplication; participants understand XP versus evidence; useful attempts and constraints are visible; findings include contrary cases. No long-term effectiveness claim.

## 9. Acceptance matrix

| Perspective | Gate |
| --- | --- |
| Engineering | Migration, invariants, failure handling, portability and explainability pass |
| Design thinking | People identify and attempt a worthwhile next move without disproportionate burden |
| OD | System recognises collective/structural work and respects authority, safety and autonomy |

All three gates matter. Software tests cannot stand in for user research; engagement cannot stand in for learning.

## 10. Dependency adoption gate

For each candidate record exact release/commit, licence, maintenance evidence, runtime/transitive dependencies, compatibility, data flows, telemetry, minimal fit test and removal cost. Do not install the shortlist wholesale. No unverified latest-version claims.

First spikes: property-based progression tests; one structured proposal behind a fake/live-approved adapter; plain transition code versus XState only if complexity warrants.

## 11. Risks and stop/adapt decisions

- Reward chasing: reduce creditable events and inspect artificial records.
- Reflection burden: shorten capture; do not require polished essays.
- AI replaces thinking: require user attempt or explanation in learning mode.
- Structural problems become personal tasks: improve routing and permit escalation/pause.
- Content abstraction spreads complexity: stop generalising until a second real use case needs it.
- Privacy ambiguity: stop outbound integration until data flows and permissions are clear.
- Capability overclaim: revise labels and evidence rules before scaling.

## 12. Explicit deferrals

No billing, SSO, multi-tenant server, marketplace, universal skills ontology, graph database, vector store, workflow builder, public rankings, employer dashboard, xAPI ingestion or full content editor in the first build.

## 13. Implementation handoff requirements

Report changed files, decisions, migration behaviour, exact checks/results, limitations, manual walkthrough and the next three product assumptions to test. Never claim a proposal was executed. Do not merge or deploy without permission.

Owners and dates remain unassigned until an implementation mandate. Use issues for active tasks; this document describes outcomes and dependencies.
